# Dynamic Agent Engine

A small FastAPI and LangChain runtime that can create internal agents for a task, select registered tools, execute the task, and keep the generated agent in a central registry.

The design is intentionally simple:

```text
Task request
    ↓
AgentRuntime
    ↓
AgentCreator / planner
    ↓
AgentSpec: name, instructions, tools
    ↓
ToolRegistry validates the selected tools
    ↓
AgentRegistry stores the generated agent
    ↓
LangChain agent executes the task
```

## What the project does

- Registers reusable tools in one `ToolRegistry`.
- Uses an LLM planner to design an agent for each task.
- Allows the planner to select only tools that are already registered.
- Creates a LangChain agent with the selected tools and instructions.
- Registers the generated agent in `AgentRegistry`.
- Executes the task and returns the generated agent name, version, and result.
- Keeps file operations inside the repository `files/` directory.

The runtime creates agents dynamically and can create missing tools from approved application-owned templates. It does not execute arbitrary Python code generated by the LLM.

Agents are work-oriented rather than one-off task objects. The planner assigns a stable `work_key` such as `research` or `file_operations`. The first task creates that work agent; later tasks with the same work key and required capabilities reuse it.

## Requirement workflow

Every task follows this sequence:

```text
Requirement
    ↓
Planner creates AgentSpec + tool requirements
    ↓
Check ToolRegistry
    ↓
Create missing approved template tools
    ↓
Append tool name/capability to registry.yaml
    ↓
Find or create work-oriented agent with the completed tool set
    ↓
Append agent name/capability to registry.yaml
    ↓
Execute requirement
```

The workflow is implemented by `WorkflowEngine`, `AgentRuntime`, `AgentCreator`, and `TemplateCreateEngine`. New tool templates are registered with `TemplateCreateEngine`; the current approved template is `web_search`.

## File-by-file guide

### `app/main.py`

Application entry point.

It:

1. Loads environment variables from `app/.env`.
2. Creates the shared LLM.
3. Creates the `ToolRegistry`.
4. Registers `read_file` and `write_file`.
5. Loads approved tool templates and restores persisted runtime objects.
6. Creates `AgentCreator` and `AgentRuntime`.
7. Defines the HTTP endpoints.
8. Includes the agent execution router.

This is the main dependency-wiring file.

### `app/registry.py`

Defines `AgentRegistry`.

The registry stores `AgentDefinition` objects by name and supports:

- Registering an agent.
- Finding an agent by name.
- Listing agent names or definitions.
- Removing an agent.

The registry rejects duplicate names and unknown lookups.

### `app/registry_instance.py`

Creates the shared process-level registry:

```python
agent_registry = AgentRegistry()
```

Other modules import this same instance so all routes and engine components see the same registered agents.

It also creates the shared `registry_catalog`, which is passed to both the tool and agent registries.

### `app/registry.yaml`

The central human-readable catalog for registered tools and agents. It is updated when:

- A tool is registered during application startup.
- Approved tool templates are loaded and persisted agents are restored.
- A new dynamic agent is created for a task.

The catalog stores metadata only. Executable factories remain in Python memory and are not serialized into YAML.

### `app/runtime_store.py`

Persists template-backed runtime objects in SQLite at `app/runtime.db`. Tool records contain the tool name, capabilities, template, function key, and arguments. Agent records contain the agent name, template, instructions, and capabilities.

On startup, `TemplateCreateEngine` reads these records and rebuilds objects from registered templates. The database stores configuration and references; it does not serialize executable Python code.

### `app/registry_store.py`

Provides the small YAML persistence layer used by both registries. It keeps the `tools` and `agents` sections in one file and exposes a snapshot for the `/registry` endpoint.

### `app/agents/models.py`

Defines the `AgentDefinition` data model.

An agent definition contains:

- `name`
- `version`
- `description`
- `capabilities`
- `factory`
- `enabled`

The factory creates the executable agent when it is needed.

### `app/agents/base.py`

Defines the abstract interface for custom application agents.

Custom agents inherit from `BaseAgent` and implement:

```python
async def run(self, input: str, **kwargs):
    ...
```

### `app/agents/llm.py`

Creates and caches the shared Groq chat model.

`get_model()` returns the same model instance for the lifetime of the process. This avoids creating a new LLM client for every request.

### `app/agents/register.py`

The application has no predefined agent now. Agents are created through the requirement workflow and restored from SQLite when a persisted template-backed agent exists.

### `app/templates/builtin_tools.py`

Contains the approved implementation functions:

- `write_file(filename, content)`
- `read_file(filename)`

File tools resolve paths below the repository-level `files/` directory and reject paths that escape it. The same module contains the approved `web_search` implementation used by the web-search template.

### `app/tools/tool_registry.py`

Defines `ToolRegistry`, the central collection of tools available to the planner and generated agents.

It supports:

- Registering tools.
- Looking up one tool.
- Looking up several tools.
- Describing tools for the planner.
- Listing registered tool names.

The registry is the security boundary for tool selection: the planner can only select tools that this registry exposes.

### `app/engine/schemas.py`

Defines the structured `AgentSpec` returned by the planner.

The planner must provide:

- A short agent name.
- A description.
- Instructions for the generated agent.
- At least one registered tool name.

### `app/engine/agent_creator.py`

Creates an agent definition dynamically.

Its flow is:

1. Describe registered tools to the planner.
2. Ask the planner to design an agent for the task.
3. Validate the selected tool names against `ToolRegistry`.
4. Create a unique agent name.
5. Build a factory for a LangChain agent.
6. Register the resulting definition in `AgentRegistry`.

The LLM output is not trusted for tool authorization. Unknown tool names are rejected by the registry.

### `app/engine/template_create_engine.py`

Creates missing tools and agents from approved `ToolTemplate` and `AgentTemplate` objects. It registers them with the runtime registries, which updates `app/registry.yaml`.

### `app/engine/workflow.py`

Coordinates the requirement workflow: planner output, tool checking, missing-tool creation, and find-or-create work-agent behavior.

### `app/templates/tool_template.py` and `app/templates/agent_template.py`

Define reusable creation blueprints. A tool template receives a name, description, capabilities, and an application-owned function. An agent template receives its name, instructions, description, and capabilities.

### `app/engine/runtime.py`

Coordinates one task execution.

It asks `AgentCreator` for an agent, creates the agent from its factory, invokes it, and returns the final message.

### `app/routes/agent.py`

Provides the endpoint for running a named registered agent:

```text
POST /agents/{agent_name}/run
```

It supports both kinds of agents in this project:

- Custom agents exposing `.run()`.
- Generated LangChain agents exposing `.ainvoke()`.

### `app/routes/runtime.py`

Owns the general runtime endpoints:

- `GET /health`
- `GET /tools`
- `GET /agents`
- `GET /registry`
- `POST /tasks`

`create_router()` receives the already-created registries and runtime from `main.py`. This keeps route logic separate from application setup while avoiding global imports and circular dependencies.

### `app/main.py`

`main.py` is intentionally limited to application wiring: configuration, model creation, registry setup, runtime creation, and router inclusion.

## HTTP API

### Health check

```http
GET /health
```

Response:

```json
{"status": "ok"}
```

### List tools

```http
GET /tools
```

Returns the tools available for dynamic agent creation.

### List agents

```http
GET /agents
```

Returns agents created through `/tasks` or restored from SQLite.

### View the YAML registry

```http
GET /registry
```

Returns the current contents of `app/registry.yaml` as JSON. This is useful for checking that a new task created and registered an agent.

### Execute a task dynamically

```http
POST /tasks
Content-Type: application/json

{"task": "Write a short summary to summary.txt"}
```

The planner selects registered tools, creates an internal agent, executes the task, and returns something similar to:

```json
{
  "agent": "file_writer_a1b2c3d4",
  "version": "1.0.0",
  "result": "..."
}
```

#### Web-search and file-creation test

Use a single line inside the JSON string. A raw line break inside the quoted `task` value makes the JSON invalid.

```bash
curl -X POST http://127.0.0.1:8000/tasks \
  -H "Content-Type: application/json" \
  -d '{"task":"Search the web for the latest FastAPI release. Summarize the release in five bullet points, include the source URLs, and save the result to fastapi_latest.txt."}'
```

The filename is relative to the sandboxed `files/` directory. The workflow should plan `web_search` and `write_file`, create/register `web_search` from its template if it is missing, create an agent, and save:

```text
files/fastapi_latest.txt
```

Each task allows at most three web-search calls and eight agent workflow steps. Search results are cached during the process, which prevents an agent retry loop from generating unlimited provider requests.

Check the result:

```bash
curl http://127.0.0.1:8000/tools
curl http://127.0.0.1:8000/agents
curl http://127.0.0.1:8000/registry
cat files/fastapi_latest.txt
```

An expected task response has this shape:

```json
{
  "agent": "research_agent_a1b2c3d4",
  "version": "1.0.0",
  "result": "..."
}
```

### Run a registered agent

```http
POST /agents/{agent_name}/run
Content-Type: application/json

{"message": "Write hello world to hello.txt"}
```

## Running locally

Create or update `app/.env` with the provider credential required by the configured model:

```env
GROQ_API_KEY=your-key-here
```

Start the API from the repository root:

```bash
uvicorn app.main:app --reload
```

Then open:

```text
http://127.0.0.1:8000/docs
```

4. `app/tools/tool_registry.py` — understand tool registration and validation.

## Design principles

- Keep orchestration in the engine layer.
- Keep tool authorization in `ToolRegistry`.
- Keep agent metadata in `AgentRegistry`.
- Keep tools small and independently testable.
- Reuse the shared LLM client.
- Validate all LLM-selected tool names before execution.
- Keep filesystem access sandboxed.

## Current limitations

- Generated agents are kept in memory and disappear when the process restarts.
- There is no persistent workflow registry yet.
- Tools must be added in code before they can be selected.
- Each task currently creates a new internal agent instead of reusing a semantically matching one.
- Authentication, rate limiting, and production observability are not implemented yet.

These limitations leave a clear path for progressive evolution without changing the basic runtime flow.
